Running snis_client in a web browser
------------------------------------

snis_client can be built to run in a web browser, using emscripten.  Only the
client runs in the browser.  snis_server, snis_multiverse and ssgl_server are
the same native programs as always.

This is new and incomplete.  What works: connecting to one snis_server
without the lobby (as in doc/lobbyless-operation.txt), or through a lobby;
every station, sound effects, keyboard, mouse, typing, gamepads, voice chat,
and the ship's computer speaking (through the browser's own speech
synthesis).  What does not, yet: finding lobbies on the local network; the
launcher.

Gamepads: a browser only reveals a gamepad after one of its buttons is
pressed, so press one once the page has loaded.  Every gamepad appears as one
joystick named "web-gamepad", which share/snis/joystick_config.txt maps for
the browser's "standard gamepad" layout (most gamepads): the right stick
steers, the left stick yaws, Y fires phasers and X torpedoes.

Voice chat: hold F12 to talk, as in the native client.  The first time, the
browser asks whether the page may use the microphone.  Browsers only allow
the microphone on https pages (or http://localhost), which snis_web_gateway
serves.  The build compiles its own Opus with emscripten (libopus-web.a),
from the same opus-1.3.1 download that DOWNLOAD_OPUS=yes uses.

Building
--------

You need emscripten (emcc).  Debian and Ubuntu package it ("apt install
emscripten"); otherwise see https://emscripten.org.  The first build downloads
and compiles emscripten's own SDL2, libpng, zlib and libvorbis, which takes a
few minutes, once.

  make WEB=1 web

This puts the client in bin/web/:

  snis_client.html	the page to open
  snis_client.js	the program, with
  snis_client.wasm
  snis_client.data	the assets, about 200 Mb
  solarsystems/		the other solarsystems, fetched when needed

The web build keeps its objects in object_files_web/, so it does not disturb
the native build in object_files/, and you can build both from one tree.

The first "make WEB=1 web" downloads the game's assets, about 700 Mb, into
web-asset-cache/, using bin/snis_update_assets (which it builds), just as the
launcher's UPDATE ASSETS button does.  Later builds reuse them; "make
mostly-clean" leaves them alone, and

  make WEB=1 web-update-assets

checks for newer ones.  The assets bundled into the client are put together
the way UPDATE ASSETS does it: the files in share/snis, with the downloaded
ones laid over them (except shaders and Lua scripts, which always come from
the source tree).  Only one solarsystem is bundled into snis_client.data,
"default" unless you say otherwise:

  make WEB=1 web WEB_SOLARSYSTEM=karado

The others go in bin/web/solarsystems/, and the client fetches one from the
gateway the first time the server puts it there, so a browser downloads only
the solarsystems it visits.  The browser's cache keeps them for next time.

Running
-------

Two things need to be running: snis_server, and snis_web_gateway, which
serves the page to browsers and connects them to snis_server.  Both are
native programs, built by a plain "make".

1. snis_server, without the lobby, on a port of your choosing:

	bin/snis_server --nolobby --port 2501 -L x

2. snis_web_gateway, told which server browsers may connect to:

	bin/snis_web_gateway --allow localhost:2501

   It serves bin/web on port 8088, and relays each browser's WebSocket to
   snis_server as an ordinary TCP connection.  snis_server needs no changes
   for this.  It relays only to the servers it has been told about, with
   --allow (which may be given more than once) or --lobby (see below).

Then open http://localhost:8088/

The page takes options in its address, all of which have defaults:

	host	snis_server's host, as the gateway sees it (default: localhost)
	port	snis_server's port (default: 2501)
	lobby	use this lobby instead of host and port (see below)
	setup	show snis_client's network setup screen instead
	ship	starship name (default: webship)
	pw	starship password (default: webpw)
	args	other snis_client options, separated by spaces

for example:

	http://localhost:8088/?ship=enterprise&pw=ncc1701&args=--navigation

With the lobby
--------------

To use a lobby, and so warp gates between solarsystems, run ssgl_server,
snis_multiverse and the snis_servers as usual, and tell the gateway where the
lobby is:

	bin/snis_web_gateway --lobby localhost

It then relays browsers to the lobby and to every game server the lobby
lists, and keeps that list up to date.  Open

	http://localhost:8088/?lobby=localhost

to join the first game server the lobby lists, or

	http://localhost:8088/?setup

for snis_client's own network setup screen, to choose the lobby, server and
ship there.  As with host above, the lobby is named as the gateway sees it.

Playing from other machines
---------------------------

Browsers only allow the threads snis_client needs on pages from a "secure
context": http://localhost is one, but http://192.168.1.10 is not.  So other
machines must use https, which the gateway serves on the same port:

	https://192.168.1.10:8088/

The first time it runs, the gateway makes a self-signed certificate naming
this machine and its addresses, and keeps it in
~/.local/share/space-nerds-in-space/web-gateway-cert.pem (and -key.pem).
Each browser warns about it once; accept it, and play.  If this machine's
address changes, delete those two files and the gateway makes new ones.  To
use a certificate of your own instead: --cert FILE --key FILE.

How it fits together
--------------------

The browser build swaps a few source files for others, chosen in the Makefile
the same way USE_GLES=1 swaps graph_dev_opengl.c for graph_dev_gles.c:

	snis_net_transport.c	-> snis_net_transport_web.c	TCP becomes WebSocket
	snis_main_loop.c	-> snis_main_loop_web.c		the browser calls each frame
	snis_asset_fetch.c	-> snis_asset_fetch_web.c	fetch solarsystems when needed
	joystick.c		-> joystick_web.c		gamepads through SDL
	snis_speak.c		-> snis_speak_web.c		the browser speaks
	(various)		-> snis_web_stubs.c		things a browser cannot do

and the WebSocket goes to snis_web_gateway, at /relay/<host>/<port>.

It always uses the OpenGL ES renderer (graph_dev_gles.c and share/snis/shader-es),
which becomes WebGL, and sound goes through SDL rather than portaudio
(WWVIAUDIO_USE_SDL in wwviaudio.c).  Everything else is the same code as the
native client.
